Tarama sonuçları bilgisayar kapatılınca kaybolabilir
webkitdirectory ile kullanıcı her seferinde aynı klasörü yeniden seçmek zorunda
chrome.fileSystem.chooseEntry + chrome.fileSystem.retainEntry + chrome.fileSystem.restoreEntry tam olarak bu sorunu çözüyor:

// İLK SEFER
const entry = await chrome.fileSystem.chooseEntry({type: 'openDirectory'});
const id = chrome.fileSystem.retainEntry(entry);
// id'yi storage'a kaydediyoruz

// SONRAKI SEFERLER (otomatik)
const entry = await chrome.fileSystem.restoreEntry(id);
// entry artık aynı klasör, kullanıcı yeniden seçmek zorunda değil
Yani Aslında Mesele Çok Basit
chrome.fileSystem API bize:

✅ Klasörü bir kez seçtirip kalıcı ID ile saklama
✅ Seçilen klasörü yeniden seçtirmeden her açılışta erişme
✅ Klasördeki gerçek dosyaları okuma (entry.getFile())
✅ Entry'leri JSON olarak kaydedip geri yükleme
Sonra dist/build yoksa:

entry.getFile('index.html', {create: false}, file => file.text()) ile ana HTML dosyasını okuyabiliriz
Build edilmiş dist klasörü için: HTML içindeki asset yollarını blob URL'lere çevirerek iframe'e yükleriz
dev server için: Gerekirse komutu kopyalarız
Yani chrome.fileSystem bir "klasör erişim" mekanizması, klasörün ne olduğuna karışmıyor. dist mi, ana proje mi, yoksa her ikisini birden desteklemek mi ayrı bir karar.

İyi soru, arcade modülünde gerçekten ciddi ve orta seviye riskler var. Hem mevcut koddan hem de mimariden kaynaklananları analiz ettim:

🔴 Kritik Seviye
1. iframe sandbox allow-same-origin
<iframe sandbox="allow-scripts allow-same-origin allow-forms allow-popups" ... />
allow-same-origin ile sandbox neredeyse tamamen etkisiz. Oyun içindeki JS:

iframe'in kendi origin'i blob:olduğu için chrome.storage.local ve IndexedDB'ye doğrudan erişebilir
parent window'a window.parent.postMessage ile müdahale edebilir
window.opener manipülasyonu ile OAuth akışlarını bozabilir
Öneri: allow-same-origin kaldırın. Sadece allow-scripts allow-forms allow-popups kalsın. Trade-off: oyun başka origin'de çalışır ama Arcade verileri tamamen izole olur.

2. HTML rewriting - sayfa içi JS doğrudan stringify ediliyor
rewriteHTML içinde index.html ham şekilde yazılıyor, içindeki <script> etiketleri korunuyor. dist klasörü kullanıcının güvenilir kaynağı olsa bile, geliştirme makinelerinde .env, *.map, .git artifact'ları blob URL'leriyle hafızaya çekiliyor. Sandbox allow-same-origin ile beraber bu dosyalar:

Memory'de object URL olarak yaşar
iframe window.map veya fetch('blob:...') ile dışarı sızdırılabilir
Iframe postMessage ile parent'a datta sızdırabilir
3. path traversal test edilmemiş
joinPath fonksiyonu .. segmentlerini destekliyor. dist/../../private/secret yazılırsa:

getDirectoryHandle("..") çağrısı mevcut rootDir içinde .. isimli alt klasörü arıyor
Pratikte olmasa da, dist klasörü rename edilirse beklenmeyen yapı oluşabilir
dist öneki gerçek bir root sınırı değil, sadece string. Hard guard yok.

🟠 Yüksek Seviye
4. Bilgi sızdırma
clipboard.writeText(devCmd) ile gerçek sistem path'i (C:\Users\emre_\Desktop\GitHub\In Progress\3D Dragon) clipboard'a yazılıyor
folderPath GameEntry'de saklanıyor
iframe context'inden bu bilgi postMessage ile sızdırılabilir
5. Manifest'te CSP / iframe kısıtı eksik
manifest.json'da content_security_policy tanımlı değil. frame-src blob: eklemediyseniz, blob URL'ler CSP'ye takılır ve hiçbir oyun yüklenmez. Veya CSP gevşetildiyse, siteler başka origin'den iframe'lenebilir.

6. Blob URL leak
URL.createObjectURL her oyun açılışında onlarca blob URL üretir. URL.revokeObjectURL hiçbir yerde çağrılmıyor. Yeni Tab her açıldığında memory kullanımı katlanarak artar.

🟡 Orta Seviye
7. IndexedDB handle'lerine XSS
handle objeleri serialize edilmeden IDB'de tutuluyor. IDB'den okurken getHandle herhangi bir doğrulama yapmıyor. FileSystemDirectoryHandle prototip manipülasyonu mümkün değil ama, type check eksik.

8. window.prompt / window.confirm
Phishing için potansiyel. Arcade kendi context'inde olduğu için düşük risk, ama "Bu oyunu kütüphaneden silmek istediğinize emin misiniz?" gibi mesajlar browser-native olarak görünür.

9. iframe permissionspolicy
allow="camera", allow="microphone", allow="payment" gibi permission attribute'ları eklenmedi. Sandbox'ta tarayıcı API'larına erişemez, ama bazı eski Chrome versiyonlarında 'bypass' mümkün.

10. console.log debug
Kod temiz görünüyor ama console.warn/error çağrıları path/handle bilgisi sızdırır (prod build'de de).

🟢 Düşük Seviye
getDisplayPath sadece okuma amaçlı, ama path sızıntısı
IDB key'leri handle_${id} deterministic, enumeration yok çünkü IDB ayrı context
Storage quota sınırı zaten Chrome tarafından korunuyor
